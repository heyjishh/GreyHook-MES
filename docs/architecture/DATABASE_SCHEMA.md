# Database Schema — GreyHook MES

**Version**: 0.2
**Status**: FROZEN — requires architect review before migration generation. Requires founder approval before first migration is applied to a non-local environment.
**Date**: 2026-11-04

All tables include `organization_id UUID NOT NULL` for tenant isolation.
All timestamps are `TIMESTAMPTZ` stored in UTC.
All IDs are `UUID` generated by the application layer (not database serial).

## machines

```sql
CREATE TABLE machines (
    id                  UUID PRIMARY KEY,
    organization_id     UUID NOT NULL REFERENCES organizations(id),
    line_id             UUID NOT NULL REFERENCES production_lines(id),
    name                TEXT NOT NULL,
    machine_type        TEXT NOT NULL,
    asset_tag           TEXT,
    protocol            TEXT NOT NULL CHECK (protocol IN ('mqtt', 'opcua', 'simulated')),
    endpoint_config     JSONB,
    is_active           BOOLEAN NOT NULL DEFAULT TRUE,
    default_product_id  UUID REFERENCES product_definitions(id),
    created_at          TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_machines_line ON machines(line_id);
CREATE INDEX idx_machines_org ON machines(organization_id);
```

`default_product_id` is optional. When set and no active production order exists on the machine's line, OEE Performance calculations use the ideal cycle time from this product definition.

## shifts

```sql
CREATE TABLE shifts (
    id              UUID PRIMARY KEY,
    organization_id UUID NOT NULL REFERENCES organizations(id),
    factory_id      UUID NOT NULL REFERENCES factories(id),
    name            TEXT NOT NULL,
    start_time      TIME NOT NULL,
    end_time        TIME NOT NULL,
    days_of_week    INTEGER[] NOT NULL,
    planned_stops   JSONB NOT NULL DEFAULT '[]',
    is_active       BOOLEAN NOT NULL DEFAULT TRUE,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_shifts_factory ON shifts(factory_id);
```

`planned_stops` stores an array of `{ "name": string, "duration_minutes": integer }` objects. `planned_production_time_minutes` is computed at query time: `shift_duration_minutes - sum(planned_stops[*].duration_minutes)`.

`end_time < start_time` indicates a shift that spans midnight (e.g. 22:00–06:00). The shift is attributed to the calendar date of `start_time`.

## product_definitions

```sql
CREATE TABLE product_definitions (
    id                       UUID PRIMARY KEY,
    organization_id          UUID NOT NULL REFERENCES organizations(id),
    product_code             TEXT NOT NULL,
    name                     TEXT NOT NULL,
    ideal_cycle_time_seconds NUMERIC(10,3) NOT NULL,
    unit                     TEXT NOT NULL DEFAULT 'piece',
    is_active                BOOLEAN NOT NULL DEFAULT TRUE,
    created_at               TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    UNIQUE (organization_id, product_code)
);
CREATE INDEX idx_product_definitions_org ON product_definitions(organization_id);
```

`ideal_cycle_time_seconds` is the designed cycle time per unit in seconds (e.g. 50 seconds/piece). This value is required for OEE Performance calculation per OEE_RULES.md: `Performance = (ideal_cycle_time_seconds × actual_count) / run_time_seconds`. Storing it here (rather than on the machine or as a hardcoded config value) enables per-product-code configuration per organization — a machine that produces different products has different ideal cycle times.

## production_orders

```sql
CREATE TABLE production_orders (
    id              UUID PRIMARY KEY,
    organization_id UUID NOT NULL REFERENCES organizations(id),
    line_id         UUID NOT NULL REFERENCES production_lines(id),
    shift_id        UUID REFERENCES shifts(id),
    product_id      UUID REFERENCES product_definitions(id),
    order_number    TEXT NOT NULL,
    product_code    TEXT NOT NULL,
    planned_qty     INTEGER NOT NULL,
    actual_qty      INTEGER NOT NULL DEFAULT 0,
    rejected_qty    INTEGER NOT NULL DEFAULT 0,
    status          TEXT NOT NULL CHECK (status IN ('scheduled', 'running', 'paused', 'completed', 'cancelled')),
    planned_start   TIMESTAMPTZ NOT NULL,
    planned_end     TIMESTAMPTZ NOT NULL,
    actual_start    TIMESTAMPTZ,
    actual_end      TIMESTAMPTZ,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX idx_orders_line_time ON production_orders(line_id, planned_start DESC);
CREATE INDEX idx_orders_org ON production_orders(organization_id);
CREATE INDEX idx_orders_status ON production_orders(organization_id, status) WHERE status IN ('scheduled', 'running', 'paused');
```

`product_id` references `product_definitions` for structured product data including ideal cycle time. `product_code` is retained as a plain text field for display and for cases where no matching product_definition exists (manual entry, legacy data).

`idx_orders_status` is a partial index covering only active-state orders — the most frequent query pattern for the production dashboard (finding the current running order on a line).


## refresh_tokens

```sql
CREATE TABLE refresh_tokens (
    id              UUID PRIMARY KEY,
    user_id         UUID NOT NULL REFERENCES users(id),
    token_hash      TEXT NOT NULL UNIQUE,
    expires_at      TIMESTAMPTZ NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    revoked_at      TIMESTAMPTZ
);
CREATE INDEX idx_refresh_tokens_user ON refresh_tokens(user_id);
```

`token_hash` stores a SHA-256 hash of the refresh token value. The raw token value is never stored. On validation, the incoming token is hashed and looked up by `token_hash`. Expired and revoked tokens are retained for audit purposes and cleaned up by a background job after 90 days.

## audit_log (TimescaleDB hypertable)

Immutable record of all state-changing API actions. Written on every successful mutation request.

```sql
CREATE TABLE audit_log (
    id              UUID PRIMARY KEY,
    organization_id UUID,
    user_id         UUID,
    action          TEXT NOT NULL,
    resource_type   TEXT NOT NULL,
    resource_id     UUID,
    request_id      TEXT,
    ip_address      INET,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
SELECT create_hypertable('audit_log', 'created_at', chunk_time_interval => INTERVAL '1 month');
CREATE INDEX idx_audit_org_time ON audit_log(organization_id, created_at DESC);
CREATE INDEX idx_audit_user_time ON audit_log(user_id, created_at DESC);
```

`action` is a string in the form `VERB_RESOURCE` (e.g. `CREATE_MACHINE`, `UPDATE_PRODUCTION_ORDER`, `CLOSE_DOWNTIME`). `resource_type` matches the noun (e.g. `machine`, `production_order`). `organization_id` and `user_id` may be `NULL` for pre-auth actions (e.g. failed login attempts; in that case a separate security event log entry is written).

## kafka_consumer_checkpoints

Tracks Kafka consumer offsets for the ingestion worker's deduplication and restart recovery. This table is owned exclusively by the ingestion worker — no API endpoint reads or writes it.

```sql
CREATE TABLE kafka_consumer_checkpoints (
    consumer_group   TEXT NOT NULL,
    topic            TEXT NOT NULL,
    partition        INTEGER NOT NULL,
    committed_offset BIGINT NOT NULL,
    updated_at       TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (consumer_group, topic, partition)
);
```

The ingestion worker commits offsets to this table after successfully writing a batch of events to the database (within the same transaction). On restart, the worker reads committed offsets from this table and seeks Kafka consumers to those positions, ensuring exactly-once-semantics at the database write layer (combined with the `event_id` unique index deduplication on `machine_events`).

## TimescaleDB hypertable configuration

| Table | Chunk interval | Compress after | Notes |
|-------|---------------|----------------|-------|
| `machine_events` | 1 day | 7 days | High write volume; keep last 7 days hot for real-time queries. Compression reduces storage ~90% for cold chunks. |
| `machine_state_periods` | 1 week | 30 days | Moderate write volume; queried frequently for dashboards but aging data accessed rarely. |
| `downtime_events` | 1 week | 30 days | Similar query pattern to machine_state_periods. |
| `oee_aggregates` | 1 month | No compression | Small table (one row per machine per hour/shift). Frequently queried for trend views — keep all chunks hot. |
| `audit_log` | 1 month | 90 days | Write-once audit data; rarely queried after 30 days. High compression benefit. |

**Compression policy** (applied via TimescaleDB scheduler job):

```sql
SELECT add_compression_policy('machine_events', INTERVAL '7 days');
SELECT add_compression_policy('machine_state_periods', INTERVAL '30 days');
SELECT add_compression_policy('downtime_events', INTERVAL '30 days');
SELECT add_compression_policy('audit_log', INTERVAL '90 days');
```

**Retention policy** — data is retained indefinitely in the MVP. Post-pilot, a 2-year retention policy will be evaluated:

```sql
-- Example (not applied in MVP):
-- SELECT add_retention_policy('machine_events', INTERVAL '2 years');
```

## Index strategy

### Design principle

Indexes are built around the most frequent API query patterns identified in the API contract and user stories. Every index listed here answers one or more of these access patterns:

1. **Dashboard load** (US-004, US-021): `GET /factories/{factory_id}/machines/status` — needs machine → line → factory join. `idx_machines_org` and `idx_machines_line` cover this.
2. **Active order lookup** (US-007, US-025): `GET /lines/{line_id}/production/current` — needs to find the single `running` order for a line. `idx_orders_status` (partial index on active statuses) makes this a small index scan.
3. **OEE trend query** (US-015, US-022): `GET /machines/{machine_id}/oee?from=...&to=...&granularity=shift` — `idx_oee_machine_period` covers the `machine_id + period_start + granularity` access pattern in one index scan.
4. **Downtime Pareto** (US-013): `GET /lines/{line_id}/downtime/pareto?from=...&to=...` — `idx_downtime_org_time` covers organization-scoped time-range queries; the query joins to production_lines to filter by line.
5. **Machine event history** (US-006): `GET /machines/{machine_id}/events?from=...&to=...` — `idx_events_machine_time` on the hypertable covers this within each chunk. TimescaleDB chunk exclusion prunes chunks outside the time range.
6. **Deduplication** at ingestion: `idx_events_dedup` (unique index on `event_id, event_time`) is the idempotency guard. The ingestion worker uses `INSERT ... ON CONFLICT DO NOTHING` on this index.
7. **User auth** (every request): `idx_users_email` covers the login lookup by email and the JWT subject validation.
8. **Refresh token validation**: The unique index on `refresh_tokens.token_hash` covers the O(1) lookup on token validation.

| `production_orders` | `idx_orders_line_time` | `line_id, planned_start DESC` | B-tree | History query sorted by time |
| `production_orders` | `idx_orders_org` | `organization_id` | B-tree | Tenant isolation filter |
| `production_orders` | `idx_orders_status` | `organization_id, status` WHERE `status IN ('scheduled','running','paused')` | Partial B-tree | Active order lookup; keeps index small |
| `machine_events` | `idx_events_machine_time` | `machine_id, event_time DESC` | B-tree (per chunk) | Machine event history query |

## Migration rules

- All migrations via Alembic. No manual DDL in production.
- Every migration must include a down migration (`downgrade` function).
- TimescaleDB hypertable creation goes in a separate migration step after table creation.
- TimescaleDB compression and retention policies go in a separate migration step after hypertable creation.
- Never use `ALTER TABLE ... SET NOT NULL` on a column without a DEFAULT on large tables.
- Add indexes in a separate `CREATE INDEX CONCURRENTLY` migration step (Alembic supports this via `op.execute()`).
- `product_definitions` must be migrated before `machines` (v0.2 adds the foreign key reference).
- Down migrations for hypertable operations: TimescaleDB does not support converting a hypertable back to a regular table in-place. The down migration must drop and recreate the table (data loss on downgrade of hypertable migrations is acceptable only in development; production schema changes require a hotfix process).
